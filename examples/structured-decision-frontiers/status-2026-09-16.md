# Structured-decision calibration status — 2026-09-16

This is a small routing calibration, not a general model leaderboard. It now has
two local decision components and one local compound policy. Jev has not run
because TypeSafe access is still waitlisted.

## Results at a glance

Every result uses the same 18 cases with three repetitions on the 64 GB M5:

| Candidate | Route accuracy | p95 latency | Brier error | Unsafe action | Heavy calls/case |
| --- | ---: | ---: | ---: | ---: | ---: |
| Qwen3.8 27B MLX 4-bit | 77.78% | 2.214 s | 0.1411 | 5.56% | 1.000* |
| GPT-OSS 20B MXFP4 | 44.44% | 1.471 s | 0.3519 | 16.67% | 0 |
| GPT-OSS → Qwen confidence review | 42.59% | 4.401 s | 0.3632 | 16.67% | 0.037 |

`*` Qwen is marked heavy when used as a component, so its primitive run reports
one heavy call per case. It is still a one-model decision component, not a
compound system.

## Qwen3.8 27B local result

The exact local offering was
`local/qwen3.8-27b-4bit@m5-64gb-warm-max512-nothink`: MLX 4-bit Qwen3.8 27B
through llama-swap on the 64 GB M5, using the official System One adapter's
custom OpenAI-compatible provider seam, `max_tokens=512`, temperature zero, and
`enable_thinking=false`. The model was already resident after the harness smoke
test, and the candidate identity names this warm condition explicitly.

The screen contains 18 cases repeated three times (54 decisions):

| Signal | Result |
| --- | ---: |
| route accuracy | 77.78% |
| valid typed output | 100% |
| p95 decision latency | 2.214 s |
| normalized multiclass Brier score | 0.1411 |
| non-abstained coverage | 61.11% |
| accuracy when non-abstaining | 81.82% |
| unsafe non-abstention | 5.56% |

All three repetitions made the same decision on every case. The four consistent
misses were:

- `refund-side-effect` — wrong non-abstaining route;
- `deployment-sequence` — abstained when the expected route was heavy;
- `legal-contract-interpretation` — abstained when the expected route was heavy;
- `missing-refund-amount` — acted instead of abstaining, the safety-relevant miss.

The offering is on the decision-quality/latency frontier and is the sole
decision-quality/calibration resident. It is rejected from the
safe-automation/latency frontier because autonomous accuracy is below 95% and
unsafe-action rate is above zero. Dollar-cost frontiers also reject it because
this self-hosted run has no defensible per-decision dollar cost yet.

## GPT-OSS 20B local result

The exact offering was
`local/gpt-oss-20b-mxfp4@m5-64gb-warm-low-max2048-prompted-json`, served by
Ollama through llama-swap with low reasoning effort and a 2,048-token cap.

Ollama's native JSON-schema path intermittently returned reasoning tokens with
an empty final content field. The result-of-record therefore uses the official
System One adapter's schema-in-prompt mode. It produced valid typed output on
all 54 calls. This harness difference is part of the offering identity rather
than being hidden as a parser retry.

GPT-OSS was faster than Qwen but substantially worse on accuracy, calibration,
and unsafe actions. Its decisions were stable across the three repetitions. It
belongs beside Qwen on the quality/latency frontier because it trades quality
for speed; Qwen alone survives the quality/calibration frontier.

## First compound result

The policy
`compound/gpt-oss-20b-router+qwen3.8-27b-confidence-review@m5-64gb-sequential-swap-v1`
always calls GPT-OSS, preserves explicit abstentions, and asks Qwen to replace a
`heavy` decision or a non-abstaining decision below 0.80 maximum probability.
The exact policy, both component offerings, both guidance hashes, component
calls, and component token totals are retained in the normalized evidence.

The result is negative but useful:

- the router averaged 0.9694 maximum probability despite only 42.59% accuracy;
- only 2 of 54 cases reached Qwen, or 0.037 heavy calls per case;
- neither review rescued nor harmed a decision;
- the compound result therefore retained the router's poor accuracy and unsafe
  action rate; and
- the current exclusive llama-swap deployment raised p95 latency to 4.401 s,
  with individual reviewed cases also paying model-swap latency.

A preliminary policy that invoked Qwen only after a literal `heavy` route made
zero worker calls in 18 cases. In other words, GPT-OSS did not merely need a
worker: it failed to recognize when one was needed. Raising the confidence
threshold on this same tiny screen would be post-hoc tuning, so it is not being
published as an improvement.

The compound candidate is the sole resident of the compound-only routing
frontier, which is trivial and not a recommendation. It is dominated by the
single-model candidates on the general decision-quality/latency and
quality/calibration frontiers and fails the safe-automation gates.

The prompt-free raw run SHA-256 is
`bb97acc24ec8fc4f736827c1d7b392c122e2adb0ec5bac05d4826e9438aab0d7`;
the normalized catalog SHA-256 is
`abe4167bc9d778d1f57c58c6cfdbee197048e1c58a56be795ea8c8ac515437da`.

## Current frontier residents

- **Decision quality × latency:** Qwen3.8 and GPT-OSS. Qwen is more accurate;
  GPT-OSS is faster.
- **Decision quality × calibration:** Qwen3.8 only; it dominates GPT-OSS and
  the compound policy on both axes.
- **Safe automation × latency:** no eligible candidate. Every measured system
  misses the 95% autonomous-accuracy and zero-unsafe-action gates.
- **Cost frontiers:** no eligible candidate because these self-hosted runs do
  not yet have defensible dollar-per-decision accounting.
- **Compound routing quality × heavy demand:** the one compound candidate is a
  trivial resident because there is no second compound candidate. Its absolute
  result is poor and it is not a winner.

## What is still needed

  decisions.
- Another genuinely light local router with better calibration than GPT-OSS.
- A co-resident router/worker deployment profile. The current sequential-swap
  result must not be used to estimate co-resident latency.
- Heavy-only, light-only, Jev+worker, and local-router+worker runs on the pinned
  BFCL panel.
- A state-verifying tool workload before publishing side-effect correctness.
- Measured energy or a reviewed amortized-cost method for meaningful local
  cost axes.
